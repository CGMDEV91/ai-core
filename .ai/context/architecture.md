# Architecture — how ai-core is put together

_Last updated: 2026-11-16 (1.0.0)_

## Two halves: the method and the tools

ai-core is a **working method** written as Markdown (commands, procedures, rules, templates) plus **deterministic
tools** in TypeScript that compute what a language model should not guess (the gate, impact, the ticket header…).
The method tells the model *what to do and when*; the tools give it *facts*. Every improvement in `history.md` is one
of three moves: a fact the model guessed is now computed by a tool, a text the model re-read every time is now read
only when needed, or a rule the model forgot is now enforced by the tool or the wiring.

## A project after the install

```
<project>/                  one repository (in-repo) — or a plain folder holding service repositories (workspace)
├─ .ai/                     its own git repository: the knowledge (ignored by the project through .git/info/exclude)
│  ├─ (framework files)     commands/ procedures/ rules/ templates/ install/ scripts/ … — replaced by every update
│  ├─ project.json          what the tools read: stacks (name, paths, exec, repo), agents — written by detect, kept by hand edits
│  ├─ orchestrator.md       the system (generated by /start; Drupal: built by `orchestrator --write`)
│  ├─ services/<name>/      service.md + context areas — integrations.md · CONTEXT.md
│  ├─ skills/ known-issues/ tickets/<KEY>/   the knowledge the work produces
│  ├─ context/              indexes (code-index.json local, callgraph.json shared, contracts, receipts/ local…)
│  └─ framework.local.json  where it was installed from (source, branch, commit, version, inRepo) — personal
├─ CLAUDE.md                only with Claude Code: @-imports of .ai/ (excluded from git)
└─ <code> / <service repos>
```

Per machine (not in the project): opencode's user config gets the `instructions` (`.ai/non-negotiables.md`,
`.ai/orchestrator.md`, `.ai/rules/*.md`, resolved against the folder opencode is opened in), the 15 command stubs, the
5 agents and the plugin stub; Claude Code's `~/.claude` gets the same commands and agents (generated) and the hooks.
One installation serves every project of the machine; in a folder without `.ai/` everything does nothing.

## The tools

- `node .ai/scripts/ai.mjs <tool>` is the entry. `ai.mjs` picks how to run TypeScript for the Node version and, on
  Windows with the project on a `\\wsl.localhost\…` path, **re-runs itself inside WSL** (git, ddev, drush live there).
- `cli.ts` dispatches to `lib/<tool>.ts` → `main(argv)`. Every `lib/*.ts` with a `main` is a tool, except the
  libraries listed in `NOT_COMMANDS` and the per-stack parts (`gate-*`, `codeindex-*`, `touchpoints-*`,
  `callpaths-*`). `--service <repo>` runs a tool inside one service of a workspace (`AI_SERVICE`, `AI_ROOT`).
- `lib/project.ts`: `AI` (the `.ai` folder), `WORKSPACE` (its parent: the repository or the workspace folder),
  `ROOT` (the service when `--service`), `cfg()` (project.json), `stack()`, `services()`.
- `setup/stack.<name>.json` (indexes to build, freshness checks) and `setup/adapter.<name>.json` (detection
  defaults) describe each stack.
- `opencode/plugin/ticket-context.ts` (header, compaction context, context size, WSL rewrite of git/drush) and
  `ticket-changes.ts` (edits → diary, lint on the spot) — loaded by the per-machine stub. Each file exports **one**
  function: opencode calls every export.
- `lib/hook.ts` does the same for Claude Code (`hook prompt|session|edit`), `lib/claude.ts` writes its wiring.

## The flow of a ticket (who does what)

`/adaptive KEY` (or `/analysis` → `/bugfix`) → `start-session.md` (time, branch) → `intake.md` (`ticket new` creates the
folder from the template; prior art; services) → impact analysis (`impact`, `touchpoints`) → plan (`/architect` when
not small) → phases: the main session delegates closed tasks to `@executor`, reviews each diff, runs `gate` (it writes
its **receipt**) → `/reviewer` (findings in `## Review`, incremental rounds, two at most) → test instructions →
`close.md` (`impact --record`, stale skills → the skill question, `receipts fold`, known issue, commit messages; the
human commits). The ticket header (`ticketctx.ts`: `header()` + `suggest()`) says on every message the step the
ticket's own state calls for; `next` prints the `▶ Next` line every command ends with.
